# Database Conventions

> **Authority:** This document defines naming and schema conventions for the ЧтоХочу
> PostgreSQL database and the mobile Drift (SQLite) store. It is normative for every
> migration and every table definition. See [`architecture.md`](./architecture.md) for the
> role of each store.

## 1. Naming

### 1.1 Tables

| Rule | Example |
|------|---------|
| snake_case | `shopping_lists`, not `ShoppingLists` or `shoppingLists` |
| Plural | `wishes`, `wishlists`, `users`, `friends` |
| Junction tables: singular_singular, alphabetical | `friend_user`, `shopping_list_user` |
| Pivot for polymorphic: follow Laravel conventions | `model_has_roles`, `taggables` |
| No database prefixes | `users`, not `cht_users` (the app schema is the default) |
| No reserved words | avoid `order`, `user` (use `users`, `orders`), `group` |

Junction table names join the two singular table names with an underscore. If the
relationship is between a table and itself (e.g. friendships), use a descriptive name
(`friendships`) rather than `user_user`.

### 1.2 Columns

| Rule | Example |
|------|---------|
| snake_case | `created_at`, `last_used_at`, `email_verified_at` |
| Foreign keys: `{singular_table}_id` | `user_id`, `wishlist_id`, `shopping_list_id` |
| Booleans: adjective or `is_`/`has_` prefix | `is_active`, `has_media`, `archived` |
| Timestamps: `_at` suffix for points in time | `created_at`, `completed_at`, `expires_at` |
| Durations: `_seconds` / `_ms` suffix with unit | `ttl_seconds` |
| Enums: singular noun, snake_case values | column `visibility`, values `public`/`shared`/`friends`/`private` |
| No abbreviations except well-known ones | `url` ok; `usr` not ok |
| No column named `data` | use a specific name (`payload`, `metadata`, `settings`) |

### 1.3 Indexes and constraints

| Object | Naming |
|--------|--------|
| Index | `{table}_{columns}_{type}` — e.g. `wishes_user_id_index`, `wishes_wishlist_id_created_at_index` |
| Unique index | `{table}_{columns}_unique` |
| Foreign key | `{table}_{column}_foreign` |
| Check constraint | `{table}_{column}_check` or descriptive `{table}_{purpose}_check` |

Laravel's migration builder generates these names by default; do not override them unless
the default collides or is ambiguous.

## 2. Primary Keys

### 2.1 UUID primary keys

All business tables use **UUID v4** (or UUID v7 where time-ordering is beneficial) primary
keys, stored as PostgreSQL `uuid` columns:

```php
$table->uuid('id')->primary();
```

- The `User` model uses `HasUuids`, `$incrementing = false`, `$keyType = 'string'`.
- All other business models follow the same pattern.
- UUIDs are generated by the application (or by PostgreSQL's `gen_random_uuid()`). They are
  not auto-incremented.
- UUIDs are stored as native `uuid` (16 bytes), not as `varchar(36)`, to save space and
  improve index performance.
- Route model binding uses the string UUID form.

### 2.2 Exceptions

Tables that are purely internal infrastructure may use bigserial primary keys:

| Table | PK type | Reason |
|-------|---------|--------|
| `personal_access_tokens` | `bigserial` | Sanctum default; token id is part of the plaintext token |
| `jobs` | `bigserial` | Laravel Queue default |
| `cache` | `string` | Laravel cache default |
| `sessions` | `string` | Laravel session default |
| `failed_jobs` | `bigserial` | Laravel default |

Spatie permission tables use UUID primary keys (per the project's migration) for
`roles`, `permissions`, and the pivots.

### 2.3 No composite primary keys

Composite primary keys are avoided. Junction tables that need uniqueness use a composite
**unique index** plus a surrogate `bigserial` or `uuid` `id` primary key, or (for Spatie
pivots) a composite primary as required by the package. New application tables use a
surrogate UUID `id` plus unique indexes for natural keys.

## 3. Timestamps

### 3.1 Standard timestamps

Every business table has:

| Column | Type | Nullable | Purpose |
|--------|------|----------|---------|
| `created_at` | `timestamp(0) with time zone`, UTC | not null | Row creation |
| `updated_at` | `timestamp(0) with time zone`, UTC | not null | Last update |

Laravel's `$table->timestamps()` creates both. They are managed by Eloquent. Use
`timestamptz` (timestamp with time zone) so values are unambiguous; the application always
writes UTC.

### 3.2 Domain timestamps

Domain-specific points in time are nullable `timestamptz` with an `_at` suffix:

| Column | Example use |
|--------|-------------|
| `email_verified_at` | Email verification timestamp |
| `completed_at` | Shopping item completion |
| `expires_at` | Token expiry |
| `archived_at` | Wishlist archival (replaces a boolean `archived`) |
| `deleted_at` | Soft delete (see §8) |

Prefer a nullable `_at` timestamp over a boolean for state transitions that have a
when-did-this-happen question. `archived_at IS NOT NULL` is more informative than
`archived = true`.

### 3.3 Precision

Timestamps use second precision (`timestamp(0)`) for business data. Millisecond precision
is used only where sub-second ordering matters (e.g. activity feeds), and even then
revision counters are preferred for ordering.

## 4. Foreign Keys

### 4.1 Always declared

Every relationship is declared with a foreign key constraint:

```php
$table->foreignUuid('user_id')
    ->constrained()
    ->cascadeOnDelete();
```

- Use `foreignUuid` (not `uuid` + manual FK) so the column type and FK are consistent.
- `ON DELETE` is explicit per relationship:
  - `CASCADE` — the child is meaningless without the parent (e.g. `wishes` when a
    `wishlist` is deleted).
  - `SET NULL` — the child survives but is detached (e.g. `personal_access_tokens` when a
    user is deleted is `CASCADE`; an activity log referencing a deleted user might be
    `SET NULL` to preserve the audit trail).
  - `RESTRICT` — the parent cannot be deleted while children exist (e.g. a user with
    active shopping lists must not be hard-deleted; use suspension instead).
- No `ON DELETE NO ACTION` (the default) without an explicit decision; it is equivalent to
  `RESTRICT` but the intent is less clear in review.

### 4.2 Indexes on foreign keys

Every foreign key column has an index. Laravel's `foreignUuid(...)->constrained()` creates
the index automatically. Composite indexes are added when the FK is commonly queried
alongside another column (e.g. `shopping_list_id, status`).

### 4.3 Self-referential

Self-referential FKs (e.g. `parent_id` on a hierarchical table) are declared with
`->constrained('own_table_name')` and use `SET NULL` or `CASCADE` per the domain.

## 5. Indexes

### 5.1 What to index

- Every primary key (automatic).
- Every foreign key (automatic with `constrained`).
- Every unique constraint (automatic).
- Every column used in a `WHERE`, `ORDER BY`, or `JOIN` clause that appears in the
  application's query patterns.
- Composite indexes for common multi-column filters, ordered by selectivity (most
  selective first), matching the sort direction used by queries.

### 5.2 Partial indexes

Use partial indexes where a large table has a common filter on a small subset:

```php
$table->index('status', 'wishes_open_status_index')
    ->where('status = 'open');  // expressed in raw SQL in the migration
```

Example: index only `open` shopping items, since `done` items are rarely queried by status.

### 5.3 Avoid over-indexing

Every index slows writes. Do not add an index without a concrete query that benefits. The
query plan (`EXPLAIN ANALYZE`) is the proof, not intuition.

## 6. Check Constraints

Use check constraints for invariants that the application cannot guarantee alone and that
are cheap to verify:

| Constraint | Example |
|------------|---------|
| Non-negative numeric | `CHECK (quantity >= 0)` |
| Range | `CHECK (revision >= 0)` |
| Enum-like (when not a DB enum) | `CHECK (visibility IN ('public','shared','friends','private'))` |
| String format | `CHECK (username ~ '^[a-z0-9_]+$')` |
| Cross-column | `CHECK (expires_at IS NULL OR expires_at > created_at)` |

Prefer a native PostgreSQL `enum` type only when the value set is stable and small and
renaming is unlikely; otherwise use a `string` + check constraint, which is easier to
extend additively (adding a value is a migration, not a type change).

## 7. JSON Columns

### 7.1 When to use

JSON columns (`jsonb`) are used for:

- **Flexible metadata** that varies per row shape and is not queried by individual keys
  (e.g. `wishes.metadata` for provider-specific attributes).
- **Sync operation payloads** (`sync_operations.payload`) that are opaque to the schema and
  interpreted by application code.
- **Settings/preferences** that are read whole and written whole (e.g.
  `users.notification_preferences`).

### 7.2 When not to use

JSON columns are **not** used for:

- Data that should be queryable by individual fields with indexes — promote to columns.
- Data that participates in relationships — promote to a related table.
- Data that has a stable, known shape — promote to columns.
- Anything that needs a foreign key, unique constraint, or check constraint on a sub-field
  — promote to columns.

### 7.3 Indexing JSON

If a JSON field is queried, index it with a functional index on the extracted path, or
promote it to a column. Do not scan a `jsonb` column without an index on a large table.

```php
// In a migration
DB::statement("CREATE INDEX wishes_metadata_source_idx ON wishes ((metadata->>'source'))");
```

### 7.4 Prefer `jsonb` over `json`

Always use `jsonb`, never `json`. `jsonb` is binary, indexable, and de-duplicates keys.
`json` preserves input formatting but is not indexable and is never worth the tradeoff.

## 8. Soft Deletes

### 8.1 Policy

Soft deletes (`deleted_at` + Eloquent `SoftDeletes` trait) are used **sparingly**, only
where:

- The data must be retained for audit/legal reasons after user-facing deletion.
- Foreign keys elsewhere reference the row and `CASCADE` would lose data the user expects
  to keep (e.g. a deleted user's wishes in a shared wishlist).
- Restore is a product requirement.

Soft deletes are **not** used as a default. Most tables are hard-deleted. The cost of soft
deletes — every query needs `whereNull('deleted_at')`, unique constraints need
partial indexes, and "deleted" rows accumulate — is only paid when the above apply.

### 8.2 When soft-deleted

- `users`: never hard-deleted (account suspension instead). If a deletion request is
  honored, the row is anonymized, not removed, to preserve referential integrity.
- `wishes`, `wishlists`: hard-deleted unless they are part of a shared context that other
  users reference, in which case they are soft-deleted with a cleanup job.
- `shopping_lists`, `items`: hard-deleted; the audit/activity log preserves the history.
- `personal_access_tokens`: hard-deleted on revocation.

### 8.3 Unique constraints with soft deletes

A unique constraint on a soft-deletable column must be a **partial unique index** that
excludes soft-deleted rows, so a deleted row does not block re-creation:

```php
$table->string('email')->unique();  // for non-soft-deletable
// for soft-deletable:
$table->index('email');
// then a raw partial unique index:
DB::statement("CREATE UNIQUE INDEX users_email_active_unique ON users (email) WHERE deleted_at IS NULL");
```

## 9. Enums

### 9.1 Representation

- Stable, small value sets with no expected additions: native PostgreSQL `enum`.
- Value sets likely to grow: `string` + check constraint (additive value addition is a
  simple migration).
- The project default is `string` + check constraint for forward compatibility, unless the
  enum is truly fixed (e.g. `visibility`).

### 9.2 Values

Enum values are lowercase snake_case, matching the API contract
([`../03-api/conventions.md`](../03-api/conventions.md) §18). The DB and the API use the
same string values; no translation layer.

## 10. Money and Quantities

- Money is stored as `numeric(19,4)` or as integer minor units (e.g. kopecks). Never as
  `float` / `double`. The choice is documented per table.
- Quantities are `integer` or `numeric` as appropriate, with a check constraint
  (`>= 0` or `> 0`).

## 11. Text and Strings

- Use `string` (varchar) with an explicit length for bounded fields (`username` 20,
  `email` 255).
- Use `text` for unbounded fields (`name`, `description`, `payload`).
- PostgreSQL `text` and `varchar` are equally efficient; the length is a constraint, not a
  performance hint. Use a length to enforce the business limit at the DB.

## 12. Nullable Columns

- A column is `NOT NULL` unless there is a real "unknown/absent" state distinct from the
  default.
- Booleans default to `false` and are `NOT NULL`.
- Foreign keys that model an optional relationship are nullable; required relationships are
  `NOT NULL`.
- Avoid nullable strings where `''` would do; prefer `NOT NULL DEFAULT ''` for required
  strings with an "empty" state.

## 13. Defaults

- Every column that can have a sensible default has one, so `INSERT` without the column is
  valid.
- Booleans default to `false`.
- Status/visibility columns default to the most common value.
- `created_at`/`updated_at` default to `now()` (Laravel manages these).
- UUIDs are generated by the application; the column has no default unless using
  `gen_random_uuid()`.

## 14. Drift (SQLite) Conventions

The mobile Drift store follows the same naming conventions (snake_case, plural tables,
`_id` foreign keys, `_at` timestamps) for consistency with the backend, with these
adaptations for SQLite:

| Concern | PostgreSQL | Drift (SQLite) |
|---------|-----------|----------------|
| Primary key | `uuid` | `text` (UUID string) |
| Timestamps | `timestamptz` | `integer` (Unix seconds) or `text` (ISO 8601) — project picks one and sticks to it |
| Booleans | `boolean` | `integer` (0/1) |
| JSON | `jsonb` | `text` (parsed in Dart) |
| Enums | string + check | `text` (validated in Dart) |
| Foreign keys | enforced | enforced (SQLite supports FKs; `PRAGMA foreign_keys = ON` is set) |

Drift schema is managed by Drift migrations, independent of Laravel migrations, because the
mobile client ships independently and must tolerate older server schemas.

## 15. Migration Authoring Checklist

A new migration MUST:

- [ ] Follow naming conventions (table, columns, indexes, constraints).
- [ ] Use UUID primary keys for business tables.
- [ ] Declare foreign keys with explicit `ON DELETE`.
- [ ] Add indexes for every FK and every queryable column.
- [ ] Add check constraints for invariants PostgreSQL can enforce.
- [ ] Set sensible `NOT NULL` + defaults.
- [ ] Define a reversible `down()` (or throw with a reason if irreversible).
- [ ] Be additive when altering an existing table in production (zero-downtime sequence,
      see [`architecture.md`](./architecture.md) §5.4).
- [ ] Not bundle a destructive change with an additive one.
- [ ] Include a test that runs `up` → `down` → `up` cleanly.

## 16. Non-Goals

- No ORM-managed schema (no `Schema::create` at runtime outside migrations).
- No denormalized business state in Redis.
- No materialized views as authoritative state (they are derived and refreshable).
- No database-level row-level security policies (authorization is enforced in the
  application via policies; PostgreSQL RLS is not used to avoid a second, divergent
  authorization layer).
